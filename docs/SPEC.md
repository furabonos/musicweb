# musicweb SPEC — 말로 만드는 재생목록 (가칭)

> 이 문서는 요구사항·범위·데이터 모델·환경 변수의 기준 문서다.
> 원 기획은 `docs/PLAN.md`, 외부 조건 확인 결과와 출처는 `docs/RESEARCH.md`, 결정 이유는 `docs/DECISIONS.md`.
> PLAN.md와 다르게 정한 곳은 **[PLAN 변경]**으로 표시했다.

## 1. 개요

### 1.1 목적

검색창에 "Central Cee - Doja와 비슷한 곡 10개"처럼 말로 요청하면 재생목록을 만들어 바로 틀어 주고, YouTube로 가져갈 수 있게 해 주는 PC 전용 공개 웹사이트.

- 쓰려고: 곡 하나에서 시작해 취향에 맞는 재생목록을 빠르게 얻는다.
- 보여 주려고: 사람 손 없이 돌아가고, 문제가 생기면 에이전트가 고쳐 PR을 올리는 구조를 실제 서비스로 운영하고 결과를 숫자로 공개한다.
- **비상업 서비스**다. 광고·유료 기능을 넣지 않는다 (D-005). 넣으려면 이 SPEC과 음악 데이터 조합을 다시 정한다.

### 1.2 사용자

| 구분                     | 할 수 있는 것                                                            |
| ------------------------ | ------------------------------------------------------------------------ |
| 로그인 안 한 사람        | 둘러보기, 공유 재생목록 보기·재생·YouTube에서 열기, 현황판(/status) 보기 |
| 로그인한 사용자 (Google) | 위 + 재생목록 만들기, 곡 빼기·바꾸기, 내 데이터·계정 삭제                |
| 내보내기 테스트 사용자   | 위 + "내 계정에 바로 넣기" (Google 심사 전, 관리자가 등록한 최대 100명)  |
| 관리자                   | 관리자 Google 계정 목록에 있는 사람. /admin                              |

PC 웹만 지원한다(최소 너비 1024px 기준). 모바일 화면은 고려하지 않는다.

### 1.3 전체 흐름

1. 곡을 검색해 고르고 곡 수·조건을 버튼으로 정하거나, 검색창에 자연어 또는 YouTube 주소로 요청한다.
2. 요청에서 기준 곡, 곡 수, 조건을 뽑는다 (4.2). 저장된 결과 → 규칙 → AI 순서로, 대부분 AI 없이 끝난다.
3. 미리 계산해 둔 비슷한 곡으로 재생목록을 구성한다 (4.3).
4. 결과를 보고 곡을 빼거나 바꾼다.
5. 사이트에서 바로 재생한다 (4.5).
6. YouTube에서 열기, 공유 주소, (테스트 사용자) 내 계정에 바로 넣기 (4.6).

## 3. 도메인 모델과 상태

### 3.1 곡(Song)과 연결(Link)

- **곡**: 음악 데이터(MusicBrainz 녹음 ID 기준)의 곡. 아티스트, 제목, 발매 연도, 장르·태그. YouTube 데이터가 아니다.
  - **정보가 적은 곡** (`lowInfo`, D-041): 사용자가 YouTube 주소·검색으로 가져왔고 음악 데이터에서 찾지 못한 곡. 음악 데이터 ID가 없고, 화면에는 연결된 영상의 제목·채널(YouTube 출처 표시, 30일 규칙)을 보여 준다. 사용자가 확인한 아티스트·곡 이름은 음악 데이터를 다시 찾는 데만 쓰고 화면에 보이지 않는다. 밤 작업이 음악 데이터에서 찾으면 보통 곡으로 바뀐다(4.4).
- **연결**: 곡 ↔ YouTube 영상 ID. 종류(`official_audio` | `official_mv` | `live` | `cover` | `remix` | `other`)와 마지막 확인 시각을 가진다.
- 연결 상태 전이:

| 현재      | 사건                                                | 다음                                               |
| --------- | --------------------------------------------------- | -------------------------------------------------- |
| (없음)    | 수집·조회로 후보 발견, 규칙 통과                    | `active`                                           |
| (없음)    | 규칙이 애매함                                       | `pending_ai` → AI 판정 후 `active` 또는 `rejected` |
| `active`  | 30일 재확인 성공                                    | `active` (확인 시각 갱신, 제목 등 갱신)            |
| `active`  | 영상 삭제·비공개·퍼가기 불가·재생 오류 101/150 반복 | `gone` (추천에서 제외, YouTube 데이터 삭제)        |
| `active`  | 관리자가 막음                                       | `blocked`                                          |
| `active`  | 25일 넘게 확인 못 함(작업 실패 등)                  | 추천에서 제외. 30일이 되면 YouTube 데이터 삭제     |
| `blocked` | 관리자가 해제                                       | `active`                                           |

- `pending_ai`·`blocked`·`rejected` 연결도 30일 규칙 대상이다. 재확인에서 영상이 없어졌으면 `gone`, 30일이 지나면 막은 기록도 지워진다(D-028).
- 곡 하나에 연결이 여러 개면 우선순위는 `official_audio` > `official_mv` > 나머지. 라이브·커버·리믹스는 요청 조건에 있을 때만 쓴다.

### 3.2 재생목록

- `draft`(생성 직후, 수정 가능) → `saved`(공유 주소 발급). 1단계는 `saved`만 공유한다.
- 곡을 빼거나 바꾼 기록은 이벤트로 남긴다 (추천 품질 지표, 2단계 재료).

### 3.3 아티스트 수집 대상

- `active` / `paused` / `failed`(연속 실패 3회 → 운영 일지와 자동 이슈).
- 추가 경로: 관리자 추가, 사용자가 찾은 아티스트(요청의 기준 곡 아티스트 중 곡 목록에 없는 아티스트, 하루 최대 50명).
- 곡 목록은 인기 아티스트로 시작해 사용자가 찾는 아티스트를 더하며 키운다. 미리 계산(4.3)과 갱신은 최근에 조회된 곡·아티스트(`lastRequestedAt`)를 먼저 한다.

### 3.4 절약 모드 (D-039, D-040)

- 서비스 상태 `normal` ↔ `saving`. 서버가 자동으로 바꾸며, 관리자의 긴급 정지(4.11, 수동)와는 별개다.

| 현재     | 사건                                           | 다음     |
| -------- | ---------------------------------------------- | -------- |
| `normal` | AI 비용 예약이 서비스 하루 상한에 닿음         | `saving` |
| `saving` | 태평양 시간 자정(카운터 초기화) 또는 상한 상향 | `normal` |

- 바뀔 때마다 운영 일지에 한 줄(켜짐·꺼짐 시각, 이유)과 `saving_mode` 이벤트를 남긴다. 같은 날 여러 번 바뀌어도 한 번씩 남긴다.
- `saving`에서 꺼지는 것: AI 요청 해석, AI 설명(4.3), 곡 연결 AI 판정(연결은 `pending_ai`로 남김). 재생목록 만들기·바꾸기·재생·공유는 그대로다.
- AI 키가 없거나 AI 호출이 실패한 요청도 같은 방식(AI 없이)으로 처리한다. 이때는 상태를 바꾸지 않고 `ai_fallback` 이벤트만 남긴다.

## 4. 1단계 범위 (MVP)

### 4.1 기록 (이벤트 로그)

- 처음부터 모든 주요 동작을 기록한다:
  - 요청 해석, 추천 단계별 결과(후보 수, 걸러진 수, AI가 지어낸 곡 수)
  - 곡 연결, 사용자가 뺀 곡·바꾼 곡
  - 외부 호출(대상, 단위·비용, 소요 시간, 결과)
  - 한도 도달, 오류, 예약 작업 시작·끝, 관리자 변경
- 이벤트에는 검색 문장, 재생목록 이름, 이메일, uid 원문을 넣지 않는다.
  - 사용자는 서버 비밀값으로 만든 해시로만 식별한다.
  - 스키마에 정의되지 않은 필드는 저장 전에 거부한다.
- 검색 문장 원문은 그 사용자의 재생목록 비공개 문서에만 있다.

### 4.2 요청 해석

- 입력 방식 두 가지 (D-040):
  - **고르기 화면 (AI 없음)**: 곡 목록에서 곡을 검색해 고르고(이름 비교 키 앞부분 일치, 최대 10개 제안), 곡 수(5~30)와 조건 버튼(라이브·커버·리믹스)을 정한다. 해석 단계가 없다.
  - **검색창 (편의 기능)**: 자연어 문장 또는 YouTube 주소(4.4 "목록에 없는 곡").
- 검색창 처리 순서:
  1. **저장된 해석**: 정규화한 문장(공백·대소문자 정리)의 서버 비밀 해시로 `parseCache`를 찾는다. 문장 원문은 저장하지 않는다. 30일 보관.
  2. **규칙 해석** (`parseFallback`): `<곡> by <아티스트>`, `<아티스트> - <곡>`, 곡 수(`15 songs like …`, `… 15곡`), 조건 낱말(live/cover/remix, 라이브/커버/리믹스).
  3. **AI 해석**: 규칙으로 기준 곡을 못 읽었고 절약 모드가 아닐 때만. 가장 저렴한 모델(지금은 Claude Haiku 5.5, RESEARCH 9)을 쓴다.
  4. 셋 다 실패하면 고르기 화면과 예시 문장을 보여 주며 다시 묻는다.
- 출력: `{ seed: {artist, title} | null, count (기본 10, 최소 5, 최대 30), include: {live, cover, remix}, locale, unsupported: (year|mood|exclude_artist|genre|other)[] }` (D-029).
  - 1단계 조건은 "라이브/커버/리믹스 포함 여부"만 받는다. 연도·제외 아티스트·분위기는 2단계.
  - 1단계에서 알아듣지 못하는 조건은 무시하고 화면에 "아직 지원하지 않는 조건"이라고 알린다.
- 검색창 입력은 데이터로만 다룬다.
  - 모델 입력에서 구분된 필드에 넣고, 도구 없이 구조화 출력만 받는다.
  - 입력 안의 지시문이 출력 형식이나 한도를 바꾸지 못한다는 테스트를 둔다.
- 입력 길이 최대 200자.
- 해석 실패나 기준 곡을 찾지 못한 경우 사용자에게 다시 묻는다(예시 문장 제시). 이 일은 `request_parse_failed` 이벤트로 남긴다.

### 4.3 추천

**미리 계산 (D-040)** — 요청 때 AI를 부르지 않기 위해 밤 작업과 첫 요청 때 계산해 저장한다.

- **비슷한 아티스트**: 아티스트마다 ListenBrainz 비슷한 아티스트(최대 30명, 점수)를 `artistSimilar`에 저장한다. 30일마다 다시 계산한다.
- **곡 숫자 묶음**: 곡마다 장르·태그·발매 연도를 고정 길이 숫자 묶음으로 바꾼다.
  - 태그 낱말 목록(`packages/shared/src/similarity/vocab`)의 낱말마다 자리 하나 + 연도대 자리. 낱말 목록을 바꾸면 버전을 올리고 전부 다시 계산한다.
  - 재료는 음악 데이터(MusicBrainz 녹음·아티스트 태그와 장르, Wikidata 장르)뿐이다. Last.fm 태그는 오래 저장할 수 없어(약관 캐시 한도) 쓰지 않는다. YouTube 제목·설명·태그는 쓰지 않는다(D-041).
  - 아티스트마다 문서 하나(`artistVectors`)에 그 아티스트 곡들의 숫자 묶음을 모은다. 요청 한 번에 비슷한 아티스트 수만큼만 읽는다.
  - Firestore 유사도 검색·임베딩 모델은 쓰지 않는다(RESEARCH 9). 시험 점수가 모자랄 때 다시 정한다.
- **범위**: 밤 작업은 인기 아티스트(수집 대상 + 최근 조회 순) 상위부터 하루 상한(6.3)만큼 계산한다(곡 수천 개 규모). 계산이 없는 아티스트는 처음 요청될 때 계산해 저장하고, 그 요청은 기다리는 동안 진행 표시를 보인다.
- 예약 작업이 AI를 써야 하면(곡 연결 애매함 판정 등) Message Batches(50% 할인)로 모아 보낸다.

**요청 처리**

1. 기준 곡 확정: 곡 목록 → MusicBrainz 검색 → (목록에 없는 곡) 4.4.
2. **저장된 결과**: 같은 기준 곡·곡 수·조건·화면 언어 조합의 결과가 `resultCache`에 있고 7일이 안 됐으면 그 곡 목록(곡 ID만, 영상 ID 없음)을 다시 쓴다. 재생할 영상은 지금처럼 열 때 고른다.
3. 후보 모으기 (목표 30~50개, AI 없음):
   - 기준 곡 아티스트와 비슷한 아티스트들의 곡 중 숫자 묶음이 가까운 곡
   - ListenBrainz 비슷한 곡 (곡 목록에 있는 것)
   - 같이 담긴 곡 (4.3a)
   - Last.fm 비슷한 곡(보조, 짧은 캐시)
4. 걸러 내기: 곡 목록에 `active` 연결이 있는 곡만 남긴다. 후보가 부족하면 4.4의 조회 순서로 연결을 찾는다. 검색은 후보용 몫(6.3) 안에서만 한다.
5. 고르고 정렬하기: 점수 = 출처별 가중치 + 아티스트 유사도 × 숫자 묶음 가까움 + 연도 가까움. 같은 아티스트가 연속하지 않게 섞는다.
   - 곡별 한 줄 이유는 겹치는 태그로 조립한 문장(예: "같은 dream pop·shoegaze, 90년대")을 화면 언어로 쓴다. 태그가 없으면 출처 문장(예: "이 곡을 듣는 사람들이 같이 듣는 곡").
   - **AI가 고르는 방식**은 시험 비교(4.9) 뒤에 정한다. 미리 계산한 방식과 점수 차이가 0.05 이내면 쓰지 않는다. 쓰게 되더라도 후보 목록 **안에서만** 고르고 목록 밖 곡은 코드가 버린다.
6. 결과 표시. 곡 수가 모자라면 모자란 대로 보여 주고 이유를 적는다.

**AI 설명 (요청 시에만)**: 결과 화면의 "자세한 이유" 버튼을 누르면 그 재생목록의 곡별 이유를 AI가 화면 언어로 쓴다. (기준 곡, 곡, 언어) 단위로 `reasonCache`에 저장해 다시 쓴다. 로그인 필요, 만들기 한도와 같은 사용자 카운터를 쓴다. 절약 모드에서는 버튼을 끄고 안내한다.

**절약 모드·AI 없음 (D-039, 3.4)**: 위 흐름은 원래 AI가 없으므로 그대로 돈다. 꺼지는 것은 AI 해석(4.2 3단계)과 AI 설명뿐이다. 화면에 "절약 모드: 자연어 해석과 자세한 이유가 잠시 꺼져 있습니다"를 보여 준다.

### 4.3a 같이 담긴 곡 (D-041)

- 재생목록을 `saved`로 바꿀 때, 그 목록의 곡 쌍마다 횟수를 1 올린다(`cooccur/{songId}`). 누가 담았는지, 어느 재생목록인지는 저장하지 않는다.
- 같은 재생목록을 다시 저장해도 두 번 세지 않는다(재생목록 문서에 집계 완료 표시).
- 서로 다른 재생목록 **3개 이상**에서 나온 쌍만 후보에 쓴다(소수 사용자 취향이 드러나지 않게).
- 추천이 고른 곡이 다시 재료가 되는 순환을 줄이려고, 사용자가 "바꾸기"로 넣은 곡과 기준 곡 쌍에 가중치를 더 두고, 가중치 상한을 둔다. 계정을 지워도 이 횟수는 개인을 식별할 수 없어 남는다(약관에 적음).

"비슷하다"는 같이 듣는 사람·같은 장르를 뜻한다. 소리 분석은 하지 않는다.

### 4.4 곡 목록 수집

- 저장하는 것:
  - 곡 정보(음악 데이터 출처)
  - 연결(영상 ID, 영상 제목, 채널 ID, 퍼가기 가능, 아동용 여부, 마지막 확인 시각)
  - 음원·영상 파일, 썸네일 파일은 저장하지 않는다.
- 매일 밤 예약 작업 (각 작업은 긴급 정지 스위치와 호출 상한을 따른다. 외부 호출 없이 지우기만 하는 정리는 예외로 항상 돈다, D-028):
  1. **수집**: 대상 아티스트의 공식 채널 → 업로드 목록에서 새 영상만 → `videos.list`로 상세 → 곡 연결 규칙 적용.
     - 공식 채널은 MusicBrainz URL 관계, Wikidata(P2397)에서 찾는다.
  2. **재확인**: 마지막 확인이 25일을 넘은 연결을 `videos.list`로 50개씩 재확인.
     - 없어지거나 비공개·퍼가기 불가가 되면 `gone`으로 바꾸고 YouTube 데이터를 지운다.
  3. **정리**: 30일을 넘긴 YouTube 데이터를 무조건 삭제한다 (실패 대비 안전장치).
- 곡을 찾는 순서 (요청 처리 중):
  1. 곡 목록
  2. MusicBrainz URL 관계·Wikidata P1651의 영상 ID → `videos.list`로 확인 (1단위)
  3. 검색 (마지막 수단, 한도 안). 결과는 곡 목록에 추가한다.
- 제목에서 곡 이름 뽑기와 종류 판별은 규칙이 먼저다. 애매한 것만 AI에게 맡긴다 (스킬 `song-matching`). 야간 작업의 AI 판정은 Message Batches로 모은다.
- **목록에 없는 곡** (D-041, 로그인 필요):
  - **YouTube 주소**: 검색창에 `youtube.com/watch?v=`, `youtu.be/`, `music.youtube.com` 주소를 넣으면 영상 ID만 뽑아 `videos.list`(1단위)로 받는다.
    - `snippet.categoryId`가 `10`(Music)이 아니거나, 삭제·비공개·퍼가기 불가면 "음악 영상이 아니거나 재생할 수 없는 영상"이라고 안내하고 멈춘다. 분류는 YouTube가 준 값만 쓴다.
    - 이미 곡 목록에 연결된 영상이면 그 곡을 기준 곡으로 쓴다.
    - 아니면 곡 연결 규칙(제목 정리)으로 아티스트·곡 이름을 미리 채운 확인 창을 보여 준다. 사용자가 확인·수정한 이름으로 MusicBrainz를 찾는다. 찾으면 보통 곡 + 연결로 추가, 못 찾으면 정보가 적은 곡(`lowInfo`)으로 추가한다.
    - 사용자별 하루 링크 입력 5회(6.3). 같은 영상은 하루에 한 번만 새로 처리한다.
  - **이름 검색**: 이름으로 요청했는데 곡 목록·MusicBrainz 어디에도 없으면 YouTube 검색 1회(기준 곡 몫, 6.3)로 상위 5개를 보여 주고 사용자가 고른다. 고른 뒤는 주소 입력과 같다. 기준 곡 몫이나 사용자 검색 한도를 다 쓰면 "YouTube 주소를 붙여 넣어 주세요"라고 안내한다.
  - 영상 설명·태그는 받지 않거나 받아도 저장하지 않고, AI에 넘기지 않는다. 사용자 입력은 데이터로만 다룬다.
  - **정보가 적은 곡의 후보**: 같은 채널의 다른 곡(곡 목록에 있는 것) + 사용자가 확인한 아티스트 이름으로 찾은 음악 데이터 태그가 가까운 곡 + 같이 담긴 곡. 화면에 "정보가 적어 정확도가 낮을 수 있음" 표시와, 근거 문장("같은 채널의 곡", "같이 담긴 곡")을 따로 보여 준다.
- 매일 밤 추가 작업 (긴급 정지 `ingest`와 호출 상한을 따른다): 4. **다시 대조**: 정보가 적은 곡을 확인된 이름으로 MusicBrainz에서 다시 찾는다. 찾으면 보통 곡으로 바꾸고 태그·숫자 묶음을 계산한다. 30일 동안 못 찾으면 더 찾지 않는다. 5. **채널 수집**: 정보가 적은 곡이 들어온 채널의 업로드 목록에서 음악 분류 영상을 하룻밤 상한(6.3) 안에서 받아 같은 방식으로 추가한다. 6. **미리 계산**: 4.3의 비슷한 아티스트·숫자 묶음 계산.
- YouTube 약관상 화면에 보이는 곡 정보에는 출처(MusicBrainz 등)를 표시한다. YouTube에서 온 정보가 아님을 알린다.

### 4.5 사이트 재생

- YouTube 공식 IFrame 플레이어. 크기 480×270 이상(최소 200×200).
  - 플레이어 위에 아무것도 겹치지 않는다. 광고·링크를 막지 않는다.
- 첫 재생은 사용자 클릭으로 시작한다. 이후 곡이 끝나면(`ENDED`) 다음 곡을 연다.
- 오류 101/150(퍼가기 불가)이면 다음 곡으로 넘어가고 `embed_blocked` 이벤트를 남긴다. 오류 코드만 담는 집계용이며 연결 상태는 바꾸지 않는다(로그인 없이 받으므로, D-032). 연결 상태는 야간 재확인이 갱신한다.
- 탭이 가려졌을 때 소리만 이어 트는 기능은 만들지 않는다.

### 4.6 내보내기와 공유

- **YouTube에서 열기** (로그인 불필요):
  - `https://www.youtube.com/watch_videos?video_ids=…` 링크. 곡 수가 링크 한도(시험으로 확인, 확인 전에는 50곡)를 넘으면 나눈다.
  - 화면에 "YouTube에서 열린 목록은 직접 저장하세요"라고 안내한다.
  - 매일 시험 문제로 동작을 확인한다. 실패하면 자동 이슈를 만들고 "곡별 YouTube 링크 목록"으로 바꿔 보여 준다.
- **공유 주소**: `/p/{playlistId}`. 누구나 보고 재생한다. 검색 문장은 공유 화면에 보이지 않는다.
- **내 계정에 바로 넣기** (테스트 사용자만):
  - 처음 쓸 때만 `youtube.force-ssl` 권한을 추가로 요청한다.
  - 새 재생목록을 만들고 곡을 넣는다. 이 앱이 만든 재생목록 ID에만 쓸 수 있다.
  - 하루 서비스 전체 5개, 사용자당 1개.
  - 테스트 상태에서는 동의가 7일 뒤 만료되므로 다시 연결을 안내한다.
- 재생과 내보내기는 `MusicService` 인터페이스 뒤에 둔다. 구현체는 YouTube 하나.

### 4.7 로그인과 사용자별 한도

- Firebase Authentication, Google 로그인만.
- 재생목록 만들기는 로그인 필수. 한도는 6.3.
- 한도에 닿으면 남은 시간과 함께 안내하고 멈춘다. 한 사용자의 한도 소진은 다른 사용자에게 영향이 없다(사용자별 카운터 분리).
- 계정과 데이터 삭제: 사용자가 직접 지운다.
  - 지우는 것: 재생목록, 비공개 문서, YouTube 연결 정보, 사용자별 사용량
  - 즉시 처리하고, 실패 시 재시도해서 7일 안에 끝낸다. 이벤트 로그의 해시는 남는다(개인 식별 불가).
- 남용 방지: App Check(reCAPTCHA Enterprise), 사용자별 10초에 1회 생성 제한, 차단 계정. YouTube 주소 입력·자세한 이유도 사용자별 하루 한도(6.3)를 둔다.

### 4.9 자동 운영과 자동 수정

- 매일:
  - 곡 목록 수집·재확인·정리 (4.4)
  - 시험 문제 실행
  - 현황판 수치 갱신
  - GitHub 수치 가져오기
- **자동 이슈**: 감지 규칙이 이상을 찾으면 GitHub 이슈를 만든다.
  - 감지 대상: 제목 해석 실패, 깨진 영상 연결, 공식 음원이 아닌 연결, 요청 해석 실패 급증, 시험 점수 하락, YouTube에서 열기 링크 고장, 예약 작업 실패
  - 같은 문제는 지문(fingerprint)으로 묶어 중복 이슈를 만들지 않는다.
  - 하루 최대 5개. 긴급 정지 스위치로 끌 수 있다.
  - 이슈 본문에는 검색 문장·재생목록 이름·계정 정보를 넣지 않는다.
- **자동 수정**: `auto-fix` 라벨이 붙은 이슈에서 Claude Code GitHub Action이 실행된다 (D-038).
  - 재현 테스트 → 수정 → PR 순서로 진행한다. 화면이 바뀌면 수정 전후 캡처(`pnpm capture`)를 PR에 붙인다.
  - 하루 실행 상한은 3회(태평양 시간)다.
  - 라벨을 붙인 사람과 이슈 작성자 모두 저장소 쓰기 권한이 있어야 실행한다.
  - Claude는 브랜치에 커밋하고, 워크플로가 제목·본문을 채운 PR 만들기 링크를 이슈에 남긴다. 관리자가 눌러 PR을 연다.
- PR 본문(템플릿 강제, CI `pr-body` 검사): 쉬운 말 요약 3줄, 화면이 바뀌면 수정 전후 캡처(CI가 찍어 올림), 테스트·시험 점수 변화, 직접 확인하는 방법.
- CI를 통과한 PR을 관리자가 확인하고 합친다. **자동 합침 없음.**
- **시험 문제**:
  - 곡 연결: 정답을 정해 둔 50곡의 영상 후보를 녹화해 둔 데이터로 연결 정확도를 잰다 (CI에서 결정적으로 실행).
  - 추천: "이 곡을 넣으면 이런 곡들이 나와야 한다" 문제로 기대 곡 포함률을 잰다. CI에서는 녹화된 후보 데이터 + 실제 AI 호출(같은 저장소 PR만)로 잰다.
    - 두 방식을 같은 문제로 잰다: `precomputed`(미리 계산, AI 없음, CI에서 항상 결정적으로) / `ai`(AI가 후보 안에서 고름). `ai`가 0.05 넘게 높지 않으면 `precomputed`를 쓴다(D-040). 가까운 장르 미끼를 넣어 문제를 어렵게 한다.
  - 기준 점수는 `evals/baseline.json`에 있고, 점수가 떨어지면 CI 실패.
  - 매일 실제 데이터로도 실행해 현황판에 올린다.

### 4.10 공개 현황판 (/status)과 운영 일지

- 서비스: 요청 해석 성공률, 없는 곡을 걸러 낸 수, 공식 음원 연결 정확도, 사용자가 뺀 곡 비율, 추천 시험 점수
- 곡 목록: 보유 곡 수, 어제 추가된 곡 수, 검색 없이 처리된 요청 비율, 오늘 남은 YouTube 호출 수(단위·검색 따로)
- AI 비용: AI 없이 처리된 요청 비율, 요청 한 건의 평균 AI 비용, 오늘 절약 모드였던 시간
- 목록에 없는 곡: 목록에 없던 요청 비율, 그중 링크와 검색의 비율, 요청으로 새로 추가된 곡 수, 정보가 적은 곡과 보통 곡의 "사용자가 뺀 곡 비율" 비교
- 자동 수정: 자동 이슈 수, PR 승인 비율과 거절 사유, 수정까지 걸린 시간, 되돌린 수정 비율, 최근 수정 10건과 PR 링크
- 마지막 갱신 시각. 숫자마다 계산 방법을 적는다. 실패와 거절도 숨기지 않는다.
- 운영 일지(시간순):
  - 예약 작업 시작·끝과 처리량
  - 발견한 문제와 자동 이슈
  - 에이전트 PR·CI 결과·승인/거절·이후 점수 변화
  - 한도 도달, 절약 모드 켜짐·꺼짐, 작업 실패, 관리자가 켜고 끈 설정
  - 항목마다 이슈·PR 링크를 단다.
- 현황판 수치는 누구나 읽고 서버만 쓴다. 검색 문장·재생목록 이름·계정 정보는 드러내지 않는다.

### 4.11 관리자 화면 (/admin)

- 긴급 정지: 재생목록 만들기 / 곡 목록 수집 / 자동 이슈 생성을 각각 켜고 끈다. 바꾸면 다음 요청부터 즉시 적용된다(서버가 매 요청마다 읽음). 절약 모드(3.4)는 자동이며 여기서는 상태만 보여 준다.
- 한도 설정: 사용자별 하루 한도, 서비스 전체 비용·호출 상한.
- 사용량 보기: 오늘 YouTube 단위·검색 횟수·AI 비용, 한도까지 남은 양.
- 수집 대상 관리: 아티스트 추가·빼기, 예약 작업 최근 결과, 수동 재실행.
- 잘못된 연결 고치기: 곡의 영상 바꾸기(그 곡이 이미 가진, 25일 안에 확인된 다른 연결로)·막기. 고친 내용을 시험 문제로 추가하자는 GitHub 이슈(`eval-case`)를 연다. 관리자가 `auto-fix` 라벨을 붙이면 자동 수정이 PR 링크를 만든다(D-043).
- 사용자 관리: 계정 차단, 내보내기 테스트 사용자 등록·해제(최대 100명).
- 보안:
  - 관리자 목록(`ADMIN_EMAILS`)에 있는 계정만 들어갈 수 있다. 권한은 서버 함수와 보안 규칙에서 확인한다(화면 숨김은 보조).
  - 모든 관리자 변경은 누가·언제·무엇을 바꿨는지 감사 기록과 운영 일지에 남긴다.
  - 관리자 화면에서도 검색 문장과 재생목록 내용은 기본으로 보여 주지 않는다.

### 4.12 약관

- 개인정보 처리방침·이용약관(한/영)에 넣을 내용:
  - 수집 정보, 보관 기간, 삭제 방법(7일 안 처리), 쿠키
  - YouTube API 사용 사실, YouTube 이용약관 링크와 동의 문구, Google 개인정보처리방침 링크, 권한 철회 방법
  - 음악 데이터 출처 표시(ListenBrainz, MusicBrainz, Wikidata, Last.fm)
  - 저장한 재생목록의 곡 조합은 누가 만들었는지 알 수 없게 횟수로만 모아 추천에 쓰며, 계정을 지워도 이 횟수는 남는다(4.3a)
- 처음 쓰기 전에 동의를 받는다(로그인 시). 모든 화면 하단에 링크를 둔다.

### 6.2 원칙 (강제 수단과 함께)

| 원칙                                                      | 강제 수단                                                                                                                                                                                                                                                        |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 사용자의 기존 재생목록은 절대 바꾸지 않는다               | `youtube-write` 어댑터는 `createPlaylist`, `addItems`만 공개한다. `addItems`는 `ytExports`에 이 사용자 소유로 기록된 ID만 받는다. 수정·삭제 메서드는 없다. 다른 곳에서 YouTube 쓰기 API를 부르면 ESLint가 막는다. 단위 테스트로 거부를 확인한다.                 |
| 사용자는 자기 데이터만 읽고 쓴다                          | 보안 규칙(기본 거부) + 함수마다 소유자 검사. 에뮬레이터 규칙 테스트로 "A가 B 데이터를 못 읽고 못 바꾼다"를 확인한다.                                                                                                                                             |
| 서비스 전체와 사용자별 비용·호출 상한                     | 모든 외부 호출은 `budget.reserve()`를 거친다(Firestore 트랜잭션, 서비스·사용자 카운터 분리). 어댑터 밖의 `fetch`는 ESLint가 금지한다. 상한 초과·긴급 정지 테스트를 둔다. Functions 예산 정지와 월 예산 알림을 설정한다.                                          |
| API 키와 연결 정보는 서버에만                             | 비밀값은 `defineSecret`으로 둔다. 연결 정보는 AES-256-GCM으로 암호화해 `secrets_oauth`에 저장하고, 규칙은 접근을 전부 거부한다. web 빌드 결과물에서 비밀값 이름·키 패턴을 찾는 테스트를 둔다. `apps/web`이 `functions`·서버 패키지를 import하면 ESLint가 막는다. |
| 비밀값 커밋과 main 직접 push 차단                         | 커밋 전 훅(secretlint), push 전 훅(main 거부), Claude Code PreToolUse 훅(main push·`--no-verify` 차단), CI 비밀값 검사(gitleaks), GitHub main 보호(PR·CI 필수, 강제 push 금지)와 비밀값 push 보호를 둔다.                                                        |
| 음원·영상 파일을 저장하지 않는다                          | 저장 스키마에 파일·바이너리 필드가 없다. Storage를 쓰지 않는다(규칙 전부 거부).                                                                                                                                                                                  |
| 플레이어를 숨기거나 변형하지 않는다                       | 플레이어 컴포넌트 하나만 쓴다. E2E가 크기 ≥200×200, 위에 겹친 요소가 없음을 확인한다.                                                                                                                                                                            |
| 할당량은 사지 않는다. 프로젝트 1개, 비공식 수집 도구 금지 | 외부 호출은 허용 목록 어댑터만 쓴다(ESLint). 웹 페이지 긁기는 금지하고, 예외는 D-006 링크 동작 확인 1건뿐이다.                                                                                                                                                   |
| 입력과 외부 글의 지시문을 명령으로 취급하지 않는다        | AI 호출은 도구 없이 구조화 출력만 받는다. 사용자 입력·외부 텍스트는 데이터 필드에 넣는다. 주입 문장 테스트를 둔다. 목록 밖 곡은 코드가 버린다.                                                                                                                   |
| 서비스 AI는 API 키로만, 요청 때 AI는 예외                 | AI는 `adapters/llm.ts`(`ANTHROPIC_API_KEY`)로만 부른다. 구독 로그인(`claude` CLI)은 `evals/`의 개발용 시험에만 쓰고 `functions/`가 import하면 ESLint가 막는다. 추천 기본 경로(4.3)는 AI 호출 0건이라는 단위 테스트를 둔다.                                       |
| YouTube 영상 정보로 곡 정보를 추론하지 않는다             | 숫자 묶음·태그 함수는 음악 데이터 타입만 받는다(타입). 링크 입력 처리는 categoryId와 제목만 쓰고, 설명·태그를 AI 어댑터에 넘기지 않는다는 테스트를 둔다.                                                                                                         |
| YouTube 데이터 30일 규칙                                  | 재확인·정리 작업을 둔다. "30일 넘은 YouTube 데이터가 남지 않는다" 테스트를 둔다.                                                                                                                                                                                 |

## 9. 나중에 할 기능

### 2단계

내 재생목록 보관함, 조건 지정(연도, 제외 아티스트, 분위기), 무한 재생, 심사 통과 후 "내 계정에 바로 넣기" 전체 공개, 할당량 증가 신청(준수 심사).

### 3단계

공개 재생목록 수집(그 곡이 든 재생목록 찾기, 추천 재료로 활용), 공연 예습 재생목록, Spotify, 언어 추가.

### 이후 아이디어

사용자가 뺀 곡·남긴 곡을 추천 재료로 반영.

임베딩 모델(Voyage 등)이나 Firestore 유사도 검색(`findNearest`): 태그 숫자 묶음의 시험 점수가 모자랄 때 검토(RESEARCH 9).

브라우저 내장 AI(Chrome Prompt API)로 요청 해석: 한국어 미지원·Chrome 전용·높은 사양 요구로 보류(RESEARCH 9). 한국어를 지원하면 다시 본다.

## 10. 리스크 & 주의사항

- **YouTube 약관 회색지대**: 여러 채널 데이터 합치기, 파생 데이터 조항.
  - 곡 정보는 음악 데이터에서 가져오고 YouTube에서는 영상 ID만 연결한다. 출처를 표시하고 30일 규칙을 지킨다.
  - 할당량 증가 심사 때 구조를 설명한다. 지적받으면 구조를 바꿔야 할 수 있다.
- **`watch_videos` 링크**: 비공식이라 언제든 깨질 수 있다. 매일 확인하고, 깨지면 대체 화면으로 바꾼다.
- **검색 100회/일**: 곡 목록이 작은 초기에는 검색이 빨리 동난다. 초기 아티스트 목록을 넉넉히 미리 수집한다.
- **ListenBrainz Labs**: SLA가 없다. 결과를 곡 목록에 반영해 의존을 줄이고, 장애 시 Last.fm·AI 후보로 대신한다.
- **Last.fm**: 비상업 전용, 표시 의무, 캐시 100MB 상한, 이용 종료 시 삭제.
- **MusicBrainz 장르 태그**: CC BY-NC-SA. 비상업이라 쓸 수 있지만 출처 표시와 동일 조건 공유가 필요하다.
- **테스트 사용자 동의 7일 만료**: 내보내기 테스트 사용자는 주마다 다시 연결해야 한다.
- **예산 알림은 결제를 멈추지 않는다**: 앱 자체 상한이 1차 방어다.
- **에뮬레이터는 Java가 필요하다**: 개발 환경(T00)에서 확인한다.
- **추정 비용은 측정값이 아니다**: 구현 후 이벤트 로그로 다시 잰다.
- **YouTube 정책의 분류 추론·합치기 금지**: 영상 정보로 장르를 추론하지 않는다(D-041). 곡 연결 규칙이 제목으로 종류(공식 음원·라이브 등)를 판정하는 것과 정보가 적은 곡의 "같은 채널" 묶음도 회색지대다. 할당량 심사 때 구조를 설명하고, 지적받으면 고친다.
- **같이 담긴 곡의 순환**: 추천이 고른 곡이 다시 재료가 된다. 3개 이상 기준과 가중치 상한으로 줄이고 시험 점수로 지켜본다.
- **태그가 없는 곡**: 음악 데이터에 태그가 없는 곡은 숫자 묶음이 비어 비슷한 아티스트·같이 듣는 곡에만 기댄다.

## 11. 1단계 완료 기준

- 로그인한 사용자 누구나 자연어 요청으로 재생목록을 만들고 사이트에서 재생할 수 있다.
- 만든 재생목록을 YouTube에서 열거나 주소로 공유할 수 있다.
- 대부분의 요청(현황판 "검색 없이 처리된 요청 비율" 80% 이상)이 YouTube 검색 없이 처리된다.
- 곡 목록이 매일 밤 사람 손 없이 갱신되고, 30일 넘은 YouTube 데이터가 없다.
- 일부러 넣은 오류 하나가 이슈 → 수정 PR → CI 통과 → 내 승인까지 진행된다.
- 한 사용자가 하루 한도를 넘겨도 다른 사용자는 영향을 받지 않는다 (테스트).
- 다른 사용자의 데이터를 읽거나 바꿀 수 없다 (테스트).
- 현황판에 실제 기록으로 계산한 수치와 운영 일지가 표시된다.
- 관리자 화면에서 긴급 정지를 켜면 재생목록 만들기가 즉시 멈춘다.
- 관리자가 아닌 계정은 관리자 화면과 관리자용 기능에 접근할 수 없다 (테스트).
- 배포되어 직접 소유한 도메인 주소로 접속할 수 있다.
- Google 앱 심사를 신청했다.
